# 战例：落实一份 PR 评审意见（全流程回放）

> 真实运行记录，应作者要求对仓库与参与者脱敏：不披露仓库名、PR/issue 编号与人名。数字来自当次运行日志，未经改动。项目背景：一个 TypeScript 插件市场类开源项目（vitest 测试体系）。

## 输入

一条用户指令：

```text
用 issue-pipeline 处理 <PR 链接>
```

PR 内容：修复一个误判 bug——宿主把清单里的 patch 声明字段读作 string 或按序数组，市场读侧只认 string，数组声明的载体包被误判「损坏」。PR 同时带上了维护者评审意见，要求两处修改：

1. 声明文件缺失时不得让其余文件继续算数——应整份声明作废；
2. 另一个新增锚点整体移出本 PR。

## 流程回放（五阶段实际走向）

| 阶段 | 实际动作 | 关键判定 |
|---|---|---|
| 同步 | 读 PR 本体 + diff + 关联 issue + 全部评审评论 | `get_me` 确认身份是 **PR 作者** → 路径 = 落实意见、推送修订、回帖 |
| 分诊 | 维护者意见逐条摘成可执行修改点 | 意见即规格：意见没点名的一律不动（混合数组滤非字符串规则明确保持原样） |
| 实现 | 本地分支先复跑 PR 声称的证据（17 个测试全绿基线）→ 按两条意见修改 → 删 5 个旧测试、补 2 个钉新规则的替代测试 | 修订并入单个 commit 再推 |
| 审查 | 双轴：Spec 轴 = 评审意见，Standards 轴 = 目标仓库自己的规范文档 | **抓出一个真缺陷**：声明作废时的报错文案误写为「该包无 bundle patch」——违反仓库自己的报错三要素规范，修复并复验 |
| 回写 | 推送修订 → PR 标题/正文随范围收窄同步更新 → 逐条回帖附证据 | 回帖以作者身份第一人称写，事实边界写清（旧缺陷注明旧有，不冒认新修） |

## 结果（真实运行数字）

```text
目标测试子集   17 → 14 个全绿（17 − 删 5 + 增 2，数目吻合）
全量测试       1893 passed / 1 skipped，exit 0（--maxWorkers=2）
typecheck      3 个 tsconfig 全过
npm run check  typecheck + build + restart-smoke，exit 0
推送后 CI      9 项 checks 全绿（含跨 5 个运行时版本的 e2e 矩阵）
```

推送后 CI 转绿用时约 5 分钟；维护者复审通过前无需人工干预。

## 这条流水线做对了什么

- **身份先行**：`get_me` 判定「处理」的含义——作者就落实意见，维护者就核验决策，第三方只能评论。三种身份三条路径，不混淆。
- **意见即规格**：评审意见是规格说明书的补丁，不是聊天记录——逐条落实，没点名的不碰。
- **基线先复跑**：动手前在 PR 分支复现声称的证据，不在坏基线上施工。
- **刨子与尺子分家**：改完换「陌生视角」双轴审查，才抓到那个文案缺陷。
- **回帖像人**：短句直说、对函数点名、证据给数字、缺陷来源交代清楚。
